FactoryDB設計

1. 材料マスタ（materials）※添加物を統合
additives テーブルを廃止し、ここにまとめます。

id, name, unit, material_type（'RAW'：原料 / 'ADDITIVE'：添加物）

2. レシピマスタ（recipes）
これでレシピテーブルは非常にシンプルになり、原料も添加物も同じように登録できます。

id, item_id, material_id, quantity

3. 製造指示・ステータス管理（production_orders）★新設おすすめ
「予定」「当日リスト」「製造中」のステータスを管理する、このシステムの心臓部となるテーブルです。

id

item_id（製品）

lot_number（割り当てられた製造ロット番号）

status（'SCHEDULED'：予定 / 'READY'：当日 / 'WIP'：製造中 / 'COMPLETED'：完了 / 'WASTED'：破棄）

scheduled_date（製造予定日）

在庫の「一時記録（製造中）」はどう管理すべき？
「製造ボタンを押すと消費されたものとして、入力データを一時記録し、製造中画面へ飛ばす」
「完了で確定、廃棄で廃棄消費に切り替え」

この「一時記録」を綺麗に処理するために、在庫トランザクション（履歴）に status または is_temporary（一時フラグ）を持たせるのが最もスマートです。

「製造」ボタンを押した瞬間:

在庫引き当てを行い、inventory_transactions に「仮消費（status='TEMPORARY'）」としてレコードを挿入します。これにより、有効在庫数がその分マイナスされます。

「完了」を押した場合:

「仮消費」のステータスを「本消費（status='ACTUAL'）」に更新します。

同時に、完成した製品の入庫トランザクション（製品在庫プラス）を発行します。

「廃棄」を押した場合:

「仮消費」のステータスを「廃棄（status='WASTE'）」に更新します（これで製造消費から廃棄消費への切り替えが完了します）。

製品は完成しないので、製品の入庫は行いません。

今後の方針（開発ロードマップ）
この規模のシステムを一度に作ろうとすると、高確率でバグの迷宮に入り込みます。以下の4つのフェーズに分けて、確実に動くものを積み上げていくのがおすすめです。

Phase 1: マスタの整理と基本画面（現在地）
materials テーブルに添加物を統合するマイグレーション（SQL）の実行。

製品一覧、削除済み一覧などの基本CRUDの完成。

Phase 2: 手動での「当日製造」とレシピ連動（コア機能）
まず「予定」をスキップし、手動で当日リストに製品を追加できるようにします。

アイコンをタップしたら、レシピ通りに材料とデフォルトのロット番号がズラリと並ぶ画面（ダイアルパッド入力含む）を作ります。

ここが一番の難所なので、まずは「製造」ボタンを押したら即座に在庫が減って完了する、シンプルな流れを先に作ります。

Phase 3: 「製造中」ステータスと一時記録の導入
Phase 2でできた仕組みの間に「一時記録（ステータス：製造中）」を挟みます。

「完了」「廃棄」の分岐ボタンを作成し、在庫の確定・切り替えロジックを実装します。

Phase 4: 「予定ページ」と自動算出ロジック（MRP）
最後に、最も頭を使う「適正在庫・有効在庫の計算ルール」を組み込みます。

注文データ（仮定）の入力から、自動で production_orders に 'SCHEDULED'（予定）データが生成されるロジックを書きます。

今の段階で画面（Thymeleaf）とJSの連携（モーダルなど）はかなり綺麗に書けているので、DBの方向性（方法3の統合アプローチ）さえ決まれば、Phase 2の「レシピ連動の入力画面」へ一気に進むことができます！
