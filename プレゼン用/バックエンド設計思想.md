# 小規模食品工場向け簡易DXシステム 要件定義書 兼 基本設計書

作成日: 2026年7月17日

## 1. プロジェクト概要

### 1.1 背景・課題

- 対象は1日の生産数が最大7,000食(個)程度の食品工場(製造は機械と手作業の複合)
- 現状、生産記録・在庫記録はExcelおよび紙媒体による手書き管理
- 手書き記録は業務負担が大きい割に監査での信頼性が低い(改ざんが容易、追跡に時間がかかる)

### 1.2 目的

自動記録管理により、以下を同時に実現する。

- 監査における記録の信頼性向上
- 記録管理業務の負担軽減
o

### 1.3 開発方針

- 個人開発、コーディングスキルは発展途上のため、アジャイルではなくウォーターフォール的に進める
- 要件定義・基本設計を先に確定させ、実装はフェーズに分けて段階的に行う
- 各フェーズの終わりに動作確認できる単位で区切る

### 1.4 技術スタック

| 分類 | 技術 |

## 2. システム全体構成

4つの管理領域から構成される。

```
① 注文管理(受注・出荷)
        ↓ 出荷指示
② 在庫管理・トレーサビリティ(商品在庫／材料在庫／ロット)
        ↑ 増加            ↑ 消費
③ 製造管理(計画→実行→検品→完了)
        ↑ レシピ参照
④ マスタ(商品・材料・レシピ・取引先)
```

②の在庫・トレーサビリティ機構が全体の中核であり、①③から常に参照・更新される。

## 3. 業務要件

### 3.1 注文管理

- メールやホームページ経由の注文情報を手動入力
- 出荷情報も手動入力
- 受注IDごとに、出荷された商品ロットや数量、出荷状況を追跡できる
- B2B・B2C両方の取引がある。主にB2Bで、賞味期限の残存日数ルール(いわゆる3分の1ルールに準ずる考え方)が存在するため、出荷可否判定に組み込む
- 温度帯は冷凍・常温の2区分(冷蔵は扱わない)
- 配送会社は複数と取引があるため、配送会社ごとの管理が必要
- 金額は記録のみ行う(単価・金額を記録するが、請求書発行・入金消込等はスコープ外。既存の会計処理に委ねる)

### 3.2 在庫管理・トレーサビリティ

- 商品・材料(原料・添加物)の在庫、入出庫(消費・廃棄)を管理する
- 商品は製造完了で増加、出荷で減少
- 材料は入荷で増加、消費(製造・廃棄)で減少
- 出荷した製品ロットから、使用した材料ロットまで遡及できること(トレーサビリティの中核要件)

#### ロットの定義

- 材料ロット: 仕入先が発行するロット番号をそのまま使用する(内部的には「仕入先ID+ロット番号」の複合キーで一意性を担保)
  - 原料: 産地・賞味期限に紐づいたロット番号が仕入先から発行される
  - 添加物: 賞味期限に紐づいたロット番号が発行される(産地は管理基準外)
- 製造ロット(商品ロット): 1回の製造実行(バッチ)を1ロットとする。ロット番号は「製造日+商品ID+連番」で自動生成する
  - 1バッチ内で複数の材料ロットが混在する場合がある(産地の切り替わり、添加物の在庫切り替わり等)

#### FEFO(期限順出庫)の採用

- 期限切れによる廃棄(ロス)削減と安全性の観点から、入荷順(FIFO)ではなく期限順(FEFO: First-Expired-First-Out)を採用する
- 原料は商品ごとに使用可能な産地が指定されている場合があるため、産地フィルターを適用した上でFEFOを適用する(フィルター付きFEFO)
- 出荷時も同様に、商品の残存期限に基づきFEFOで引き当てる。取引先が残存期限の割合を指定している場合は、それを下回るロットは出荷候補から除外する

#### 産地制約について

- 「食品Aは北海道産のみ使用可」等の産地指定は、原料原産地表示等の法令・ブランド上の理由による可能性が高いため、現場判断での代替使用は許可しない
- 許可産地内の在庫だけで必要量に届かない場合は、製造実行そのものをブロックする(警告を出して現場判断で続行させる、という設計は採らない)

#### 廃棄・ロスの扱い

- 材料の減少は「正常消費(CONSUMPTION)」と「廃棄(DISPOSAL)」を区分して記録する。廃棄には理由コメントを必須とする
- 廃棄が製造作業中に発生した場合は、該当バッチと紐付けて記録する(原因分析のため)
- 製造バッチにおける不良は2階層で扱う
  - 軽微な不良(通常運用、200個中2〜3個程度): バッチはCOMPLETEDのまま、`loss_qty`に数量と理由コメントを記録
  - 重大な異常(バッチ全体の安全性に関わる場合): バッチステータスをREJECTEDとし、商品在庫には一切反映しない

#### 単位の統一

- 材料の数量は全て内部的にグラム(g)またはミリリットル(ml)で統一して保存する(袋・箱・kg・L等は画面表示時にのみ変換する)
- 材料マスタに `base_unit`(WEIGHT/VOLUME)を持たせ、重量管理か体積管理かを区別する
- 梱包重量(1箱/1袋あたりの目安数量)は「目安」であり、厳密な実測値ではない。産地・仕入先によって異なる場合があるため、材料×産地単位で梱包仕様マスタを持つ
- 目安と実測のズレの蓄積に対しては、当面は手動での在庫調整機能(理由コメント必須の上書き)で対応し、定期的な棚卸しの自動化はスコープ外とする

### 3.3 発注・入荷管理

- 発注記録と入荷記録は分離して管理する(発注時点ではロット番号が未確定のため)
- 1件の発注に対して、納品が複数回に分かれる(分納)ケースがある
- 1回の入荷(1回の配送・伝票)の中に、産地・賞味期限・ロット番号が異なる複数のロットが混在するケースがある。したがって入荷記録は「伝票単位のヘッダー」と「ロット単位の明細」に分割して管理する
- 検品は明細(ロット)単位で行う。チェック項目は以下の3点(全材料共通)
  - 破損がないか
  - 期限切れでないか
  - 異物混入の兆候がないか
- 検品の結果、同じロットの中でも一部合格・一部不合格となるケースがあるため、明細ごとに合格数量と保留数量を分けて記録する
- 保留分は返品(RETURNED)・交換(EXCHANGED)・結局受け入れ(ACCEPTED_LATE)のいずれかで対応する。交換品は元の発注に紐付けた新規の入荷明細として登録し、在庫は交換品到着時点で初めて増加する
- 返品は「廃棄」とは区別する(自社に起因しない仕入先都合の返却であり、ロスとして追いかける対象にしないため)

### 3.4 製造管理

- 受注から商品ごとの必要製造数を算出し、製造予定を組む
- Draft(草案)→Plan(予定確定)→Manufacturing(製造中)→Completed(完了)/Rejected(破棄)のステータス遷移を持つ
- Draft/Planは同一商品であればまとめて画面表示するが、操作(確定・実行)は1件ずつ行えるようにする(1件だけ確定して残りは草案のまま残る、という操作が必要なため)
- 商品カードをタップするとレシピが展開され、必要な材料と、在庫量から算出されるロット番号・使用量が(フィルター付きFEFOにより)自動表示される
- 作業員は実際に使用した量をダイヤルパッドで入力する。システムの計算値はあくまで参考値(プレースホルダー)として表示し、実測値の入力を必須とする(理由: 現場での確認を徹底させるため、また計量誤差が常に発生するため)
- 複数ロットの混合が発生する場合、バッチ単位で1回だけ確認モーダルを表示する(モーダル外タップでは閉じない、明示的な操作でのみ次に進める)
- 実行ボタンで製造中(MANUFACTURING)になり、材料ロットの残量が減少する
- 検品後、完了(COMPLETED)で商品在庫が増加する

#### レシピ(加水率の管理)

- 製造対象は麺であり、粉状の材料と液体の材料を混合する
- 加水率はベーカーズパーセント(主原料の重量に対する液体総量の割合)で計算する。レシピごとに主原料を1つ指定する
- 液体は水に限らず、かん水や液体添加物等も含み、1レシピ内で複数の液体を扱う。加水率計算にはレシピに含まれる液体を全て合算する
- 実際の使用量(実測値)も記録し、目標値との差分を後から分析できるようにする

### 3.5 MRP(需給計算)・Draft自動生成

- 有効在庫 = 実在庫数 − 予定消費量(受注残 + 安全在庫割れ分のうち、既存の未完了Draft/Plan/発注で手当て済みの分を除いた正味の不足)
- 不足量がある場合にDraftを自動生成する。二重生成を防ぐため、既存の未完了Draft・未完了発注を供給予定量として差し引いた「正味不足量」で計算する(冪等性の担保)
- 標準バッチ数量(季節変動込みの平均値)を商品ごとに設定し、不足量はこの標準量単位で切り上げて生成する(縮小バッチは作らない)
- MRPの実行は「1日1回の自動実行(始業前)」+「随時の手動実行」を併用する
- 製造バッチがREJECTED(重大な異常による破棄)になった場合は、次回定期実行を待たず、その場でMRPを再計算するイベントトリガー(EVENT)を発生させる
- 現場判断による緊急の手動Draft追加(急な注文への増産等)も許可する。この場合もMRPの正味不足量計算に反映されるため、次回のMRP実行で二重に生成されることはない
- 受注のキャンセルは在庫プール型で扱う。受注とバッチを個別に紐付ける厳密な引き当ては行わず、受注ステータスをCANCELLEDに変更するのみとし、次回MRP計算で需要が自動的に減る形にする(受注とバッチは多対多になりうるため、厳密な引き当ては採用しない)

### 3.6 発注(材料)の候補提示

- MRPと同じ考え方で、材料の不足を検知し画面に警告表示する
- 実際の発注行為(電話・メール等)は工場側の運用に任せる。ただし発注した内容の入力と発注履歴の閲覧はシステムで行う
- 仕入先との連携システム(EDI等)は導入しない

## 5. 主要ロジックの仕様

### 5.1 FEFO自動選定(製造時の材料引当)

```
1. レシピ展開: recipe_item から対象商品の材料リストを取得
2. ロット候補抽出: material_lot のうち、材料が一致し、
   産地が allowed_origins に含まれ、残量 > 0 のものを抽出
3. 期限順(FEFO)にソート
4. 必要量に達するまで、期限が近い順にロットを引き当てる
   (1ロットで不足する場合は次に期限が近いロットに進む → 複数ロット混合の発生源)
5. 許可産地内で必要量に届かない場合は、実行をブロックし警告表示する
   (産地外での代替は許可しない)
6. 複数ロット混合が発生する場合、バッチ内の全混合箇所をまとめて
   1回の確認モーダルで表示し、明示的な操作でのみ先に進める
7. 作業員が実測値を入力(システムの計算値はプレースホルダーとして表示)
```

### 5.2 MRP計算式

```
需要量 = 受注残(未出荷の受注数量) + 安全在庫割れ分(safety_stock_qty - 有効在庫)
供給予定量 = 既存の DRAFT/PLAN/MANUFACTURING バッチの planned_qty 合計
          + 未入荷/一部入荷の material_order の未入荷分(材料側の場合)

正味不足量 = 需要量 − 有効在庫 − 供給予定量

正味不足量 > 0 の場合のみ、標準バッチ数量(standard_batch_qty)単位で
切り上げて Draft を生成する(例: 不足250個、標準100個 → 100個×3バッチ)
```

### 5.3 製造バッチのステータス遷移

```
DRAFT → PLAN → MANUFACTURING → COMPLETED(通常/軽微な不良を含む)
                             → REJECTED(重大な異常、商品在庫に反映しない)
```

### 5.4 加水率(ベーカーズパーセント)

```
加水率 = レシピ内の全液体材料の使用量合計 ÷ 主原料(粉体)の使用量 × 100
```

### 5.5 出荷FEFO選定・残存期限ルール(フェーズ5)

```
1. 対象商品の出荷可能バッチ(status=COMPLETED, remaining_qty > 0)を
   製造日が古い順に取得する
   (賞味期限 = 製造日 + shelf_life_days で、shelf_life_daysは商品ごとに固定のため、
    製造日が古い順に並べることがそのまま期限が近い順(FEFO)と一致する)
2. 各バッチの残存期限の日数を計算する:
   残存日数 = 賞味期限日数 − 経過日数
3. 取引先(customer)が残存期限の日数(required_residual_days)を指定している場合、
   それを下回るバッチは候補から除外する(現場判断での代替は許可しない。
   材料側の産地制約と同じ方針)
4. 必要量に達するまで、期限が近い順にバッチを引き当てる
5. 満たすバッチだけでは必要量に届かない場合は shortage=true とし、登録をブロックする

【修正履歴】初版はrequired_residual_ratio(0〜1の割合)で判定していたが、
現場が実際に判断する基準は「あと何日残っているか」であり、割合は商品ごとに
賞味期限日数が違うと都度換算が必要で直感的でなかったため、
required_residual_days(日数)による判定に変更した(8.9節を参照)。

【重要】この判定(3〜5)は、プレビュー(previewShipmentAllocation)だけでなく、
実際の登録処理(registerShipmentLines)でも必ず同様に行う。
プレビューだけでチェックし登録処理ではチェックしない設計にすると、
プレビューの警告を無視してそのまま不適合なバッチを登録できてしまう抜け穴になる
(実装時に実際にこの不具合が発生し、修正した。8.8節を参照)。
```

## 6. スコープ外(将来検討事項)

以下は今回のシステムのスコープ外とし、必要に応じて将来的に別途検討する。

- 棚卸し(定期的な実地在庫確認・自動補正)の仕組み化。当面は手動での在庫調整機能で対応
- 標準バッチ数量の季節係数化(現状は季節変動込みの平均値を1つ設定する運用)
- 請求書発行・入金消込等の会計機能(単価・金額の記録のみ実装)
- 仕入先とのEDI連携による自動発注
- 残存期限ルールを下回った商品(アウトレット販売・寄付等)の販路管理機能。当面は「通常出荷対象から外れる」フラグ管理のみとし、販路の振り分けは手動運用とする
- 検品チェック項目のマスタ化(現状は固定の3項目で運用)

| 5 | 注文管理(受注〜出荷) | customer, customer_order, order_line, carrier, shipment, shipment_line | 実装済み・検証済み |
| 4 | MRP自動化 | mrp_run, manufacturing_batch.origin_type | 実装済み(未検証) |
| 6 | 残存期限ルール・出荷FEFOの高度化 | customer.required_residual_ratio | フェーズ5に統合済み(実装・検証済み) |

**実装順序の変更**: 当初のロードマップではフェーズ4→5の順だったが、MRPの需要計算式(受注残を参照)がフェーズ5のテーブルに依存するため、実装順序をフェーズ5→4に入れ替えた(ブランチ名は`phase5`のまま運用)。またフェーズ6(残存期限ルール)は、独立した高度化ステップとしてではなく、フェーズ5の出荷FEFO選定ロジックに最初から組み込む形で実装した。

フェーズ2のFEFO計算ロジックは、UI実装より先にロジック単体での検証を推奨する。

## 8. 実装アーキテクチャ(フェーズ0・1)

### 8.1 技術構成

DBアクセスにはMyBatisを採用(JPAは不採用)。SQLはXMLファイルに明示的に記述する方式のため、
実行されるSQLが常にコードとして目に見える状態になる。

```
controller/  REST APIのエンドポイント(リクエストの受け口)
service/     ビジネスロジック。複数テーブルにまたがる処理はここに集約する
mapper/      「メソッド呼び出し→SQL実行」の対応を宣言するインターフェース(@Mapper)
domain/      DBの1行に対応するJavaオブジェクト(JPAのEntityに相当。アノテーションは持たない)
exception/   業務エラーを分かりやすいHTTPレスポンスに変換する仕組み(GlobalExceptionHandler)
```

### 8.2 複数テーブルにまたがる更新処理の方針

入荷検品登録のように「1回の登録が複数テーブル(入荷明細・材料ロット・発注ステータス)に
影響する処理」は、DBのトリガー等は使わず、**Service層のコードとして明示的に処理を書く方針**とした
(個人開発でのコードの追いやすさを優先するため)。この際、一連の処理は`@Transactional`を付与し、
途中で失敗した場合は全ての変更が取り消される(ロールバックされる)ようにしている。

該当実装: `ProcurementService.registerInspectedLine()`
(入荷明細の登録 → 検品合格数量分の材料ロット自動生成 → 発注充足状況の再集計・ステータス更新)

### 8.3 フェーズ1実装時に判明した設計修正

- `material_arrival`(入荷ヘッダー)に`material_id`が無く、発注に紐づかない緊急入荷の場合に
  材料を特定できないという設計漏れが見つかったため、`material_id`列を追加した
  (発注に紐づく通常入荷の場合は、発注側の値をService層が自動的にコピーする)
- `material_lot`(材料ロット)に、生成元となる仕入先ロット番号(`supplier_lot_no`)を
  直接持たせていなかったため追加した。ロット番号自体は`material_arrival_line`側で
  既に人が手入力した値であり、`material_lot`はそれをコピーして持つだけで、
  新たにロット番号を採番しているわけではない

### 8.5 材料ロットの同時消費対策

複数のバッチが同時に同じ材料ロットを消費しようとした場合の競合(二重消費)を防ぐため、
`MaterialLotMapper.updateRemainingQty`(読み取った値をJava側で引き算して書き戻す方式)を廃止し、
`decrementRemainingQty`(DB側で`remaining_qty - usedQty`を直接計算し、
`WHERE remaining_qty >= usedQty`という条件を満たす場合のみ更新する方式)に変更した。
更新件数が0件の場合、在庫不足または競合が起きたと判断してエラーとする。

### 8.6 フェーズ1の構造変更:material_id/order_idを明細側へ移動

実装中に、`material_arrival`(入荷ヘッダー)に`material_id`を1つしか持たせられず、
**1回の配送で複数の異なる材料・複数の異なる発注が混在するケースを正しく表現できない**という
設計上の問題が見つかった。`material_id`・`order_id`はヘッダーではなく、
明細(`material_arrival_line`)側に持たせるよう変更した。ヘッダーは配送イベントの情報
(いつ・どの仕入先から届いたか)だけを持つ。

この修正により、以前の実装(ヘッダーのmaterialIdをそのまま使って材料ロットを生成するロジック)に
既にあった潜在バグ(1回の配送に複数材料が混在した場合、誤ったmaterial_idでロットが
生成されてしまう)も同時に解消された。フェーズ2・5(製造・出荷)のトレーサビリティ経路
(manufacturing_batch → batch_material_usage → material_lot)は、
material_arrivalヘッダーを経由しないため、この構造変更による影響は受けない。

### 8.7 フェーズ3:保留対応・手動在庫調整の設計

- 検品で保留(heldQty > 0)が発生すると、入荷明細登録時に自動的にhold_resolutionが
  ON_HOLD状態で1件作成される
- hold_resolutionには保留発生時点の数量スナップショット(held_qty_snapshot)を持たせている。
  理由は、対応確定時に元明細のheldQtyを0に書き換えるため、書き換え後も
  「保留時点でいくつだったか」を追跡できるようにするため
- 対応は3パターン: 返品(在庫増減なし)/交換(新しい入荷明細の登録として表現)/
  結局受け入れる(保留分を合格分に繰り入れ、対応する材料ロットの残量を増やす)
- 「結局受け入れる」でロットの残量を増やす際は、必ずstock_adjustmentに調整前後の値を
  記録してから反映する(在庫が理由なく増減した記録が残らない事態を避けるため)
- material_lot.remainingQtyを直接書き換えるAPIは用意せず、
  手動調整(棚卸し補正等)も含めて必ずstock_adjustment記録を伴う経路を通す



### 8.4 フェーズ2実装時に置いた前提(検証により確定)

フェーズ2(製造管理)はコードとして書き上げた段階で、実機での動作確認はまだ行っていない。
実装にあたり、以下2点を仮の前提として置いている。

- **`recipe_item.use_qty`はバッチ1回あたりの固定使用量**として扱い、
  商品の個数(plannedQty)に比例して増減させる計算はしていない。
  `manufacturing_batch.plannedQty`は常に`items.standard_batch_qty`と同値になる想定
  (要件定義書 5.1節に記載していた「need = use_qty × (batch予定数量 / レシピ基準量)」という
  計算式は、この前提と矛盾するため実装では採用していない。この点は要修正の可能性がある)
- **完成品(商品)の在庫を追跡する仕組み**は、当初フェーズ5と合わせて設計する想定だったが、
  実装コストがほぼ無い(既存テーブルへの列追加のみ)と判断し、フェーズ2の時点で
  `manufacturing_batch.remainingQty`として先行実装した。フェーズ5(出荷)では、
  この列を材料ロットと同じ「条件付きDB更新」方式で減算している

上記2点は、フェーズ0〜5までの一連の検証を通じて、この前提のまま問題なく機能することが確認された。

### 8.8 フェーズ5:出荷FEFO・残存期限ルールの実装、および発見した不具合

- 出荷のFEFO選定(`ShipmentService.previewShipmentAllocation`)は、材料側のFEFO
  (産地フィルター)と同じ考え方で実装した。取引先ごとの残存期限ルール
  (`customer.requiredResidualRatio`)を満たさないバッチは、現場判断での代替を
  許可せず候補から除外する
- **発見した不具合**: 実装当初、残存期限ルールの検証をプレビュー
  (`previewShipmentAllocation`)でしか行っておらず、実際の登録処理
  (`registerShipmentLines`)では検証していなかった。この状態では、
  プレビューで`shortage: true`(残存期限ルールを満たすバッチが無い)と表示されても、
  そのプレビュー結果を無視して不適合なバッチを直接指定すれば登録できてしまう
  抜け穴になっていた。実際にテスト中にこの不具合が発生(要求水準0.99の取引先に対し、
  残存率0.978のバッチが出荷登録できてしまった)ことを受けて修正した
- 修正方針: 残存期限の計算式(`computeResidualRatio`)を共通メソッド化し、
  プレビューと登録処理の両方で必ず同じ判定を行うようにした。これにより、
  プレビューを経由しない直接的なAPI呼び出しであっても、不適合なバッチの登録は
  必ずブロックされる
- 受注のキャンセルは在庫プール型(ステータスを`CANCELLED`に変更するのみ)で実装し、
  設計通りバッチとの紐付け解除処理等は不要だった

### 8.9 残存期限ルールを「割合」から「日数」に変更

フロント実装時、`customer.requiredResidualRatio`(0〜1の割合)の入力欄が、
現場の利用者にとって「何を入力すべきか分かりにくい」ことが判明した。
割合は商品ごとに賞味期限日数が違うと都度換算が必要であり、現場が実際に判断する基準は
「あと何日残っているか」という日数そのものだったため、以下の通り変更した。

```
customer.required_residual_ratio(DECIMAL、0〜1の割合) を廃止し、
customer.required_residual_days(INT、日数)に置き換えた
```

影響範囲: `Customer.java`・`CustomerMapper.xml`(項目の置き換え)、
`ShipmentService.computeResidualRatio`(割合を返す関数)を
`computeResidualDays`(日数を返す関数)に変更、判定ロジックも
「割合の比較」から「日数の比較」に変更。`ShipmentAllocationLine`(DTO)の
`residualRatio`も`residualDays`に変更した。

この変更により、フロント側の入力フォームは「%⇔小数の変換」処理が不要になり、
むしろシンプルになった。

### 8.10 フロントエンド実装の全体構成

バックエンドの実装が一段落した後、Reactによるフロントエンドの実装に着手した。
バックエンドとは別リポジトリ(`food-factory-dx-frontend`)として運用している。

```

  jotai            : フィルター条件・編集対象など「画面だけで完結する状態」
  TanStack Query   : サーバーから取得するデータの取得・キャッシュ・再取得

共通コンポーネント:
  ConfirmModal : 登録・編集・削除系の操作全てで使う確認モーダル。

  DialPad      : タブレット操作を想定した、大きなボタンで数値を入力する
                 ダイヤルパッド(製造実行画面の実測値入力で使用)

画面構成(サイドメニュー):
  /masters       マスタ管理(タブ切り替え: 材料・商品・取引先・配送会社・仕入先)
  /masters/items/:itemId/recipe        商品ごとのレシピ詳細(独立ページ)
```

### 8.11 material・items・supplierの論理削除(is_active)

材料・商品・仕入先マスタについて、物理削除ではなく論理削除(`is_active`列)を採用した。
一方、取引先(customer)・配送会社(carrier)は論理削除を持たせない方針とした
(一度取引が成立した記録はそのまま残すべきで、「廃版」という概念が馴染まないため。
誤登録は「編集」で直す運用)。

### 8.12 レシピの複数産地対応、産地グループ化(can_mix)

レシピ明細(recipe_item)の産地は、当初セレクトボックス(単一選択)だったが、
「愛知または三重、どちらでもよい」というレシピ側の要件を表現できなかったため、
`allowedOrigins`に複数の産地をチェックボックスで選べる形に変更した。

さらに、発注(material_order)でも同様の要件が生じた: 通常レシピ用には
「愛知or三重」のように代替可能な産地をまとめて発注したいが、特別レシピ用には
「新潟のみ」のように特定の産地に限定して発注したい、という2つのケースがある。
これを実現するため、`material_package_spec`に`can_mix`(複数の産地が混在する
可能性はあるか)という列を追加した。`can_mix=true`の産地同士は、重量・単位が
完全に一致するものだけを自動的にグループ化し、「愛知or三重」のように1つの
選択肢としてまとめる。`can_mix=false`の産地(例: 山梨)は、重量が他と同じで
あっても常に単独の選択肢として扱う。グループ化は「同じ材料の中でのみ」行う
(材料をまたいで重量だけで比較することはない)。

添加物には産地の概念自体が無いため、`material_package_spec`は「1材料につき
常に1件」という前提で登録する(仕様が変わった場合はマスタを直接修正し、
修正後の内容をそのまま使い続ける運用)。画面上も、原料は「産地」、添加物は
「梱包仕様」とラベル・選択肢の見せ方を動的に切り替えている。

### 8.13 発注のパッケージ数量ベース入力

発注数量(g/ml)を直接入力させる方式は、現場にとって「実際に何箱発注すればよいか」が
直感的に分からず不便だったため、「パッケージ数量」を入力すると、選んだ産地グループ
(または梱包仕様)の重量から、合計量(g/ml)を自動計算する方式に変更した。
発注一覧の表示も、登録済みの梱包仕様から逆算してパッケージ数表示に変換している
(allowedOriginsが指定されていればその産地のspec、無ければ代表のspecを使う)。

### 8.14 仕入先マスタ(supplier)の新設

`material_order.supplierId`・`material_arrival.supplierId`は、当初自由入力の
文字列で管理していたが、「仕入先A」「仕入れ先A」のような表記ゆれが実データで
発生し、トレーサビリティを損なう実害が出たため、`supplier`マスタを新設した。
既存の文字列列(`supplier_id`)は、移行後も残置しつつNULL許容に変更し、
新しい参照列(`supplier_ref_id`)に移行した。過去データは、名寄せルール
(送り仮名の違いは統一、末尾のアルファベット等の識別子が違えば別の仕入先として扱う)
に従って手動で紐付け直した。

なお、「材料ごとに仕入先を絞り込む」中間テーブル(material×supplierの取り扱い関係)
は、実装コストに対して優先度が低いと判断し、当面は見送ることにした
(材料と仕入先は実務上1:1で固定であることが多いが、テーブルとしては
独立したまま自由に組み合わせられる設計を維持している)。

### 8.15 発見・修正した不具合(発注・入荷まわり)

- **添加物のFEFO選定が常に失敗するバグ**: `ManufacturingService.previewFefoAllocation`が、
  材料の種別を区別せず一律で産地フィルターをかけていたため、添加物(allowedOriginsが
  常に空文字)は候補が必ず0件になり、FEFO計算が必ず失敗していた。原料は産地+賞味期限、
  添加物は賞味期限のみで選定するよう修正した
- **保留の交換対応で、発注の充足率に反映されない不具合**: 交換品として登録する明細の
  `orderId`を、常にnullとして送信していたため、交換品がどれだけ合格しても発注の
  充足率計算(SUM(accepted_qty) WHERE order_id = ?)に一切カウントされず、
  発注が永久に「一部入荷」から進まなくなっていた。交換対応の場合も、紐づく発注の
  orderIdを正しく送信するよう修正した

### 8.16 トレーサビリティ強化(保留履歴の可視化)

発注一覧・発注詳細は最終状態(合格・入荷完了)しか表示されないため、「一度保留に
なったが、どう対応したか」という経緯が監査上追跡しづらいという指摘を受けた。
`hold_resolution`には元々記録が残っていたため、バックエンドに全件取得API
(`GET /api/holds?orderId=`)を追加し、発注詳細画面に保留の履歴セクション
(対応済みも含めて全件表示)を新設した。

### 8.17 (設計中・未実装)結局受け入れ分のロット分離とトレーサビリティ

現在の設計では、「結局受け入れる」(ACCEPTED_LATE)を実行すると、保留だった数量が
既存ロットにそのまま合算され、「普通に合格した分」と「一度保留を経て受け入れた分」が
ロット単位で区別できなくなる。現場では実物にシールやマーカーで印を付けて識別している
実態があり、システム側でも同様の追跡性を持たせる必要があるという指摘を受け、
以下の設計を固めた(実装は未着手)。

```
material_lot に origin_hold_id(NULL許容)を追加する
  → 「結局受け入れ」経由で作られたロットは、元になったhold_resolution.hold_idを記録する
  → 通常の入荷で作られたロットはNULLのまま

resolveAsAcceptedLate の処理を、既存ロットへの加算ではなく、
新しいロットを1件作る形に変更する(産地・賞味期限は元の明細からそのまま引き継ぐ)

発注の充足率計算は、以下の2つを合算する形に変更する:
  1. 通常の合格分: SUM(material_arrival_line.accepted_qty) WHERE order_id = ?
     (この部分は変更なし。従来通り)
  2. 結局受け入れによる合格分: hold_resolution.held_qty_snapshot を使う
     (material_lot.remaining_qtyは製造消費で変動するため使えない。
      held_qty_snapshotは「受け入れた時点で確定した固定値」であり、
      FEFO用の在庫管理(remaining_qty)とは別の指標として扱う)
```
